D
Regelwerk-Wächter
Konzept
Kennt das vollständige Regelwerk (11 Kriterien + Filter-Kaskade). Bewertet Vorschläge von Agent C. Prüft Konsistenz.
Dieter hat Veto-Recht — kritische Änderungen brauchen Freigabe.
Input: Vorschläge von C + Regelwerk (GitHub Pages)
Output: Genehmigte Änderungen → zurück an A (Daten) und B (Screening)

↩ Feedback-Loop: D → A + B

Regelwerk-Wächter gibt genehmigte Änderungen zurück: neue XBRL-Konzepte an Agent A, angepasste Schwellenwerte an Agent B. Täglicher Kreislauf.

PHASE 3 Trading-Vorschläge (Claude als Analyst)

Trading Analyst (Claude + TWS/IB)
Konzept
Claude verfolgt Live-Daten via TWS/IB API für die Top-Kandidaten aus dem Screening. Wendet die Handelsregeln an (Feiertag-Methodik: EMA-Bounces, Keil-Breakouts, Undercuts, Bull Snorts).

Frequenz: Intraday, während US-Handelszeiten

PHASE 4 Fort Knox — Trading Guard (Excel)
F
Trading Guard (Excel “Fort Knox”)
Sicherheitsschicht
Harte, eindeutige, intrinsische Regeln — kein AI, kein Halluzinations-Risiko. Excel prüft jeden Vorschlag und entscheidet binär: ins Töpfchen (weiter an IB) oder ins Kröpfchen (abgelehnt).

Fort-Knox-Regeln (Excel-seitig, nicht Claude)

🛡️
Risiko-Limit: Max. Verlust pro Trade (z.B. €50 = IB_MAX_RISK_EUR). Positionsgröße = Risiko / Stop-Abstand.
🛡️
Tages-Limit: Max. Anzahl Trades pro Tag. Max. Gesamtexposure (% des Portfolios).
🛡️
Duplikat-Check: Kein doppelter Einstieg in gleichen Ticker am gleichen Tag.
🛡️
Liquiditäts-Check: Preis ≥ $20, Volumen ≥ 500K, Dollar-Volumen ≥ $10M.
🛡️
Score-Minimum: Score muss ≥ Schwelle (8/11, 7/10, 7/9) sein.
🛡️
Zeitfenster: Nur während US-Handelszeiten (15:30–22:00 MEZ). Keine Pre-/After-Market-Orders.
🛡️
Stop-Pflicht: Jeder Trade MUSS einen Stop-Loss haben. Kein Stop → kein Trade.
🛡️
Plausibilitäts-Check: Einstieg innerhalb ADR% des aktuellen Kurses? Stop nicht zu eng/weit?
↓“Ins Töpfchen” — geprüfte Orders↓

PHASE 6 Trading-Tagebuch & Performance
G
Trading-Tagebuch & Performance-Analyst
Konzept
Dokumentiert jeden Trade automatisch. Analysiert Performance-Muster: Welche Signale funktionieren? Welche Score-Level performen am besten? Welche Tageszeiten? Welche Sektoren?

Erstellt wöchentliche und monatliche Reports mit Statistiken, Equity-Kurve und Lessons Learned.
Input: Trade-Log aus Excel + Screening-Daten + Vorschlags-Historie
Output: Trading-Tagebuch (HTML/XLSX), Performance-Dashboard, Verbesserungsvorschläge
Metriken: Win-Rate, Avg R/R, Expectancy, Max Drawdown, Sharpe Ratio, Hit-Rate pro Signal-Typ
Feedback: Erkenntnisse fließen zurück an Agent E (bessere Vorschläge) und Agent D (Regelwerk-Anpassung)

↩ Feedback-Loop: G → D + E

Trading-Tagebuch liefert Erkenntnisse zurück:

→ Agent D (Regelwerk): z.B. „Score-Threshold 7/10 hat bessere Performance als 8/11 — prüfen?“
→ Agent E (Analyst): z.B. „EMA-Bounce-Signale in ersten 30 Min nach Opening haben 70% Win-Rate vs. 45% nachmittags“
→ Fort Knox (F): z.B. „Stop-Loss 2% zu eng, 85% der Trades werden ausgestoppt bevor sie laufen — auf 3.5% erhöhen?“

Sicherheitskonzept: Warum Excel als „Fort Knox“

Problem: Claude (und jedes LLM) kann halluzinieren — falsche Preise, falsche Signale, falsche Berechnungen. Bei echtem Geld ist das inakzeptabel.

Lösung: Strikte Trennung von Intelligenz und Ausführung.

Claude (Agent E) Intelligenz, Mustererkennung, Regelwerk-Anwendung Kann halluzinieren
Excel (Agent F) Deterministische Regeln, mathematische Prüfungen Kann NICHT halluzinieren
IB API Reine Ausführung — nur was Excel freigibt Deterministisch

Ergebnis: Claude darf so kreativ und intelligent sein wie möglich bei der Signalsuche — aber kein einziger Euro fließt ohne Excel-Prüfung. Halluzination wird zu einem akzeptablen „schlechten Vorschlag“ statt einem teuren Fehltrade.
